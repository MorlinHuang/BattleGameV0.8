# 《查手机》特效与打击感

## 开工前必须问清

1. **这个效果要表达什么？** 打击感 / 战况读数 / 信息传达，三者做法完全不同。
2. **同屏最多几个？** 决定用不用对象池、池满怎么处理。
3. **改完怎么验？** 特效必须拍胶片看，不能靠想（见 `chashouji-verify`）。

## 一、配色：这张底图不让你"更亮"

底图是明亮客厅（浅绿墙、米色地板）。**加色混合的可见度取决于底图离饱和还有多远，
而这里几乎为零——亮度这条通道整个失效。** `lighter` 白闪 **0.22 就到顶**，
再高直接过曝糊掉人物。

同一个病在三处各暴露过一次：全屏白闪叠成一片白 / 对抗线光柱走 lighter 只剩一团雾
（这就是用户说"表现力特别差"的根因）/ 奶白火花 + 浅米碎片在胶片上根本看不见。

**规则**：

| 要表达 | 做法 |
|---|---|
| 发光 | 高饱和**暖橙** `EMBER = [255,156,38]`，靠**色相**跳出来 |
| 实体 | 深色 + 描边 `INK = [58,44,38]`（取角色线稿那个暖黑），靠**轮廓**跳出来 |
| 自发光 | **边缘光**：物品自己的剪影染成高饱和色，外撑几个像素垫在本体下 |

粒子有 `edge` 描边字段——跟赛璐璐角色有线稿是同一个道理，这类画风里"看得见"
本来就靠轮廓。

**"把它改成深色"往往是绕开这条规律，不是在用它。** 做礼物物品时撞过一次：白相纸
的照片在这张底图上看不见，我把整张压成复古棕——看得见了，**但不再像照片**。规律
说的是"靠轮廓"，不是"别用浅色"。回到浅相纸 + 描边加粗到 3.6 的深棕框，两个目标
才同时成立。判据：**修完之后那个东西还是不是原来那个东西？**

同一条的另一种用法：一个配方里可以让**不同粒子分担不同职责**。奶茶泼溅的浆是浅
焦糖（负责"湿了一片"、糊住不动），可见度整个交给**深褐色的珍珠**扛。不必逼着每
一种粒子都自己解决对比度。

**自发光别给大。** `r*2.5 + alpha 0.88` 会把浅粉被子整块洗成发光板，格纹和翻角
全没。它是物体边缘的一圈光，不是一团雾 —— 光一旦厚到能盖住物品自己的描边，
读出来就是物品底下垫了个发光的影子。

**"淡"往往不是给小了，是光画在了看不见的地方；而加浓是错的解法 —— 该换的是
形状。** ★这条走了两轮才落地，两轮的读数都在，值得连着看：

第一轮诊断对了一半：色晕画在本体**下面**，中心浓向外衰减的圆形放射光，最浓的中心
整块被物品盖住，露出来的只有边缘那一圈 —— 实测 alpha 只剩 0.22（横向）0.09（竖向），
再乘 gk 就是 0.03~0.16，九成能量画给了看不见的地方。于是把渐变改成**环形**、峰值
挪到本体轮廓那一圈（0.63）。可见发光像素涨 3.6 倍，单点亮度不变。

**但用户的评价是"面积太大、特别假、像物品阴影"。** 根因是第一轮没碰的那一半：
**这张贴图是圆的，而物品不是。** 圆环贴不住方的、扁的、带把手的轮廓 —— 浓度堆上去
之后，露出来的不是"物体边上的一圈光"，是一个比物品大半圈的椭圆光斑，压在物品
底下就读成影子。浓度不是这里的自变量，形状才是。**圆形渐变贴图做不出轮廓光，
调参调不出来，别在这条路上耗。**

**自发光要贴轮廓，光的形状只能取自物品自己的剪影**：把贴图 `source-in` 染成 AURA 色，
向外撑几个像素，垫在本体正下方。露出来的就是紧贴轮廓的一圈薄光。两个可调入口是
**宽度（像素）**和 **alpha**，形状对了之后浓度反而可以放心给。

**剪影图集取三分之一分辨率。** 全分辨率八件要多吃 69MB（原图＋残影剪影已经两份），
三分之一是 7.6MB —— 这是同一条路当初被内存否决、后来又走通的全部差别。而且放大
回去时双线性插值自带两三个像素的过渡，边就从"一道实色描边"变成了"一圈光"，
不用再做模糊：**这里"糊"是特性不是缺陷**。
必须**逐格烘、格间留 2px 空边**：整张缩小的话相邻格互相采样，而打包时并集就是格
边长，长轴正对镜头那几帧物品正好顶到格边，糊过去就是邻格渗进来一道杂色。

形状对了之后，圆形色晕贴图还留着，但降级去干它本来该干的活：**只摆在身后当弹道
余辉**（不再画在本体下面），所以渐变也退回中心浓 —— 没有本体遮挡的余辉团，环形
会读成烟圈。

量它用**没有干扰色的那一件**当探针：客厅底图里没有任何青色，所以青色手柄的
发光像素数是干净的 A/B 指标；粉色件会被睡衣和抱枕污染。

**同一条弹道上"发光层"和"实体层"必须用不同色系。** 色晕、亮芯（光，靠色相）和
轮廓残影（形状，靠轮廓）全用同一个高饱和色会融成一条实色带，形状就没了——
残影改用 `TAIL` 暗调后才读得出。

## 二、弹道三层（`ammo.js`）

```
① 弹道余辉  AURA 色表 → aura(rgb) 预渲染圆形贴图，**只在身后**摆两团
            中心浓的普通放射光；不画在本体下面（圆的贴不住轮廓，见上一节）
            强度 gk = 0.11 + p.near * 0.17  ——「飞到哪儿了」一路烧起来
② 暗拖尾 + 亮芯   梯形暗带 alpha 0.30 + 楔形亮带 alpha 0.48
③ 轮廓残影   贴图 2 个 / 矢量 4 个，只画剪影，TAIL 暗调，alpha 0.40 - k*0.068
④ 边缘光    物品自己的剪影染成 AURA 色，外撑 1.5 + r*0.020 px，垫在本体下
            alpha 0.30 + p.near * 0.24。自发光**全部**来自这一层
⑤ 本体      贴图 SPRITE 那一格 / 矢量 ITEM 画法
```

**拖尾长度按距离算，不按帧数：**

```js
const TRAIL = 16, TMASK = 15;
const reachOf = (p) => Math.max(p.r * 2.6, Math.abs(p.vx) * 0.09);
```

固定回溯 8 帧时，被子 850px/s 只退了 113px，而被子本身就有 156px 宽——
整条拖尾埋在本体底下，画了等于没画；同样 8 帧，发卡（1400px/s、半宽 22）
却能拖出四个身长。**眼睛读的是"拖了多长"，那是距离不是时间。**
大件按身长拖，快件按速度拖，两条各自都会在另一头失效，所以是 `max`。

**残影不画完整物品。** 缝线、按键、格纹在高速移动里糊成噪点，而且四个残影 =
四遍完整物品，是 `ammo.js` 最贵的一笔开销。残影只需要形状 → 单独一张 `SILH` 表。

## 三、顿帧必须有不应期（`fx.js`）

顿帧的设计前提是**一次孤立的重击**——冻住之所以有力，是因为它打断了流动。
每秒九次命中时没有"这一击"可言，每次都冻就等于不冻，只剩画面不动这个副作用。

实测：连点时 **65% 的帧被顿帧冻住**，而帧均值 2.98ms、掉帧率 0.2%。
把礼物间隔放宽三倍冻结率还是 64.8%——**撑起它的不是礼物密度，是"每一击都冻"
这条规则本身**。

```js
function hitStop(sec) {
  if (sec <= 0) return;
  if (cool > 0 && sec <= lvl) return;   // 不应期内只接受更重的一击
  stop = Math.max(stop, sec);
  lvl = sec;
  cool = sec * 3;                        // 冻 sec，再流动 2*sec，占空比封顶 1/3
}
```

主循环里的档位：`Particles.hitStop(power >= 3 ? 0.11 : power >= 2 ? 0.07 : 0)`
——**点赞级（power 1）不顿帧**。一串八颗各冻 35ms 会把"哒哒哒"拆成八次停顿，
而它的表现力全在快。

**连带的坑**：顿帧冻住时走逻辑时钟的弹幕也停住、飞不到线上，在池里堆积。
`fire()` 池满时原本静默丢弃**新**发射的——观众刷了礼物屏幕上什么也不飞。
改成回收最老的那一发（`act` 按发射顺序排，队头飞得最久、离对抗线最近）：

```js
if (act.length >= MAX) pool.push(act.shift());
```

效果：110ms/件 冻结率 65.0% → 30.2%；300ms/件 17.1%。
弹幕池 均 53.8 峰 78 → 均 32.5 峰 48。

## 四、粒子（`fx.js`）

- **淡入用绝对时间，不能按寿命比例**——按比例会让长寿命粒子迟到三分之一秒。
- **颜色串和贴图在 spawn 时预生成**（`p.fill` / `p.line` / `p.tex`）。写在 draw 里
  就是每帧、每颗粒子重拼一次字符串、让浏览器重新解析一次颜色——场上常有三五百颗，
  一秒钟要算上万次。
- 池 `MAX = 1200`，实测峰值 862，够用。
- 配方在 `main.js` 的 `RECIPE`：`thud` / `feather` / `star` / `debris` /
  `petal` / `splash`（档 3）/ `bloom` / `memory`（档 4 绽放式）。
- kind 共八种。发光三种 `dot` / `spark` / `ring`（无描边，它们本来就该是光），
  实体五种 `soft` / `chip` / `star` / `heart` / `card`（吃 `edge` 描边）。

**`chip` 的语义是"空中翻滚的薄片"，需要稳定矩形时必须另开 kind。** 它带描边时
圆角被拉到 `min(w, hh*2) * 0.5`（短边收成半圆），外加按 `cos(rot * 1.7)` 压扁，
而 `rot` **初值就是随机的**——粒子一出生就被压扁了，`vrot` 调到多小都没用。
做照片雨时在这儿卡了两轮才想明白：调参数是修不好的，那是补丁。`card` 因此诞生
（不压扁、不圆角、带一块内芯）。`heart` 同批加的：负重力往上飘。

**尺寸参数乘上分量系数 `s` 之后会失控。** 档 4 的 `s = 2.8`，`r: (15 + rand*16) * s`
得到半径 42~87，一颗爱心 190px 宽、占屏宽五分之一，四十二颗把两张脸全糊死——
而脸是这个玩法仅有的两个可读信息之一。**密度靠数量，不靠单颗更大**（这条在
`feather` 的注释里早写过一次，还是又踩了）。写 `r` 时先把最高档的 `s` 乘进去算一遍。

## 四之二、转盘贴图的引擎侧（`ammo.js` 的 `SPRITE` / `fx.js` 的 `SHAPE`）

八件飞行物和实体类粒子都走 Blender 渲的转盘图集（素材侧见 chashouji-art 第五节）。
**发光类粒子 `dot` / `spark` / `ring` 保持矢量** —— 它们本来就该是光，贴图给不了加法混合。
`?nosprite=1` 同时关掉两套贴图退回矢量，改动前后对拍用它。

**转轴用 `lean`（斜角度数），别用 `axis` 三选一。** 绕观察轴能让每帧都认得出，
代价是物体自身一帧没转 —— 36 帧只是同一姿态的 36 个旋转副本，就是一张 2D 贴纸
在打旋。这条踩过：八件里七件这么渲，用户一眼看出"不够 3D"。

**验收要量投影面积，别只用肉眼**：屏幕内旋转不改变投影面积，真翻转会。
逐帧数 alpha 像素取 `(max-min)/min`，十个点以下基本就是贴纸
（实测贴纸版的手柄 3.1%，真翻面的花束 80.6%）。等价说法：36 帧的剪影
如果全都能互相旋转重合，那就是贴纸。

⚠️ **但转法对了也可能还是没有体积感**——真正的主尺是**剥掉外轮廓之后剪影里还剩
多少结构**（花束 46%、手柄 14%、抱枕 4%、发卡 0%）。转轴和转速都调不动这个数：
实测把手柄换成花束那一套转轴，后半程反而糊成一根黑香肠。整套量法与建模对策见
`danmu-3d-sprite`。

**可读性判据不能推到 36/36** —— 推到极端就会把立体感全换掉。2/3 的帧
读得出题材就够，剩下的留给体积感。

**转速按"飞行途中转半圈"定，不是转一圈。**（早先写的"必须转够一圈以上才看得出
厚度"是错的，而且错得贵——按它给出来的 14~15，每帧要转 14°，而转盘每格才 10°，
等于**每帧跳 1.4 格**，已进走马灯区：眼睛读不出"一个刚体在转"，只读到一连串跳变的
形状，也就是"闪"。用户原话是"不够三d，没有体积感"。）

半圈就够——从正面转到背面，可见面已完整换过一遍；而每帧只转 5~8°（半格到 0.8 格），
姿态是连着的，眼睛跟得上。`spin = π / 飞行时长`，按各自速度算：
volley 0.36s → 8.8、single 0.56s → 5.7、heavy 0.47s → 6.7（heavy 带 900 的加速度）。
处决弹速度减半、时长翻倍，`fire()` 里把转速一起减半，仍是半圈。

**总共只转半圈时，起始相位决定一切。** 别用 `Math.random() * 6.283` 满圈随机——
落在"手柄两个握把正好重叠成两团圆"那种相位上，观众一整发都没看见过手柄长什么样。
从第 0 格（建模时的正面）起步、抖 ±10°，齐射八颗才不至于整齐划一。

`GIFT` 表里八件都要显式给 `spin`，别让它去取 style 的默认值。

**画面内旋转与转盘旋转要分开给。** 贴图已经在转了，再让 canvas 全速跟着转就是
"又翻又转"，还会把渲好的光影一起转走 —— 那正是换 3D 要解决的问题。但完全不转
canvas 又僵。最终：转盘格子走 `p.rot` 全速（物体在翻面），canvas 只跟着转四分之一
（`p.seed + p.rot * 0.25`，它在画面里打旋）。

**粒子贴图渲白 + 运行时 `multiply` 染色**，不要把颜色烧进贴图 —— 配方是逐颗定色的
（羽毛五颗里有一颗偏粉、碎片按深浅分两种）。染好的图按 `形状|rgb` 进 `tintCache`。
代价是配方里的 `edge`（描边色）和 `lw`（描边宽）对贴图粒子失效，这是贴图路线的固有
代价，靠"描边渲中灰"部分补偿。

**细长件的绘制倍率要手工调，且绘制尺寸必须取正方形。** `pack_atlas` 算的 `scale`
对物品准（主体直径占满 2.0），但羽毛长宽 1:2.2，在正方形格子里只占一半宽度，照算出的
倍率画比矢量版细一圈，画面上碎成一片瓜子壳 —— `feather` 1.03→1.40、`debris` 0.83→1.00。
绘制尺寸取 `Math.max(p.w, p.h)`：格子是按并集正方形裁的，物体在里面保持自己的长宽比，
再按 `w×h` 去拉伸等于把比例乘两遍，羽毛会被拉成一根面条。

## 五、聊天气泡（`bubble.js`）

这个玩法争的是一部手机，而手机里有什么此前画面上一个字都没交代——观众看得到
两个人在拔河，看不到他们**为什么**拔河。

**位置按底版量出来的**：用 PIL 把 `bg.jpg` + 一张角色帧合成带坐标网格的图，
一眼看出手机在 y≈650、脸在 520~610，而 **y=150~470 那片墙完全空着**。
气泡从手机正上方升起、穿过两人中间那条缝，停在墙上——不挡脸也不挡手。

**上下两个硬边界**：下边界是出生点（手机上方 44px，那里是沙发）；
上边界是血条 y=74~105。约束 `RISE + 3*STACK ≤ 341`，现取 `RISE=140, STACK=64`。

**只有最新一条带尾巴**（`b.st === 0`）。都带尾巴读起来是每条从下面那条冒出来的——
而它们其实都来自同一部手机。

**四类消息**：`text` 日常给密度 / `hot` 暧昧给动机 / `sys` 撤回·正在输入 /
`voice` 语音条。**后两类什么都没说，反而最让人往下想。**
全程不出现露骨的词——观众自己脑补的永远比写出来的狠，这同时是平台红线要求。

按权重随机，日常最多、关键的几句要稀。越僵持发得越急
（`gap = (1.5 + rand*1.3) * (1.35 - struggle*0.5)`）——五五开时两边谁也拽不动，
画面信息量最少，正好让手机替他们说话。

## 六、层次顺序

```
底版 → 角色帧 → 对抗线/指针 → 刻度尺 → 气泡 → 弹幕 → 粒子 → HUD → 全屏闪
```

**对抗线必须画两遍**：一遍在角色之下当背景光柱，一遍以 ~0.4 强度盖在角色之上。
两个人正好在中间抢手机，只画在下面的话它全程被两具身体挡死，
而它是这个玩法唯一的战况读数。

## 七、"卡顿"先别当性能问题

帧率满格、画面不动，观众读到的同样是卡。排查这类问题**必须同时量三个数**：
帧耗时分布、掉帧率、**冻结帧占比**。只看前两个会得出"没问题"的错误结论。
量法见 `chashouji-verify`。
