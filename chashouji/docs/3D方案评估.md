# 礼物物品改用 3D 模型 + 3D 粒子：实现方案评估

> 状态：**路线 A 已拍板，玫瑰花束试点已完成**（结论见第六节）。

---

## 零、先纠正两个前提

### 0.1 当前物品不是 2D 图片，是**代码画的矢量**

`ammo.js` 的 `ITEM` 表里每件物品是一个函数，用 `ctx.roundRect` / `arc` / `bezierCurveTo`
现场画出来的几何形。所以这件事不是"2D 图片 → 3D 模型"，而是"矢量代码 → 别的什么"。

这也正是它看着简陋的根因：`chashouji` 那份 skill 的欠账清单第 1 条写的就是
**"六件飞行物仍是代码画的几何剪影，抱枕读作粉色方块"**，并标着"离 60 分最近的一段路"。
**所以真正要解决的问题是"物品太简陋"，3D 只是候选手段之一，不一定是最好的那个。**

### 0.2 Unity 版不是 Unity 原生实现，是网页画笔的 C# 翻译

| | 渲染体系 |
|---|---|
| 网页版 | 纯 Canvas 2D，**零 WebGL**（全仓 grep 结果为 0） |
| Unity 版 | 只有一个 `Vertex2D.shader` + `Core/Draw2D.cs`，**把 Canvas 2D 画笔逐字翻成了 C#** |

Unity 那边没有用 Sprite、没有用粒子系统、没有用任何 3D 管线——它就是一块画布加一支笔。
这是"网页版是单一真源、C# 逐字对照搬"这条铁律的实现方式。

**结论：引擎里跑真 3D，等于同时推翻两端的渲染体系。** 下面路线 B 的代价全部由此而来。

## 一、3D 到底能买到什么

拆成物品和粒子两件事，结论**不一样**。

### 1.1 物品：有三项真实收益

1. **旋转时光影正确。** 当前是整张图形跟着 `rot` 一起转，**高光和阴影也跟着转** ——
   物理上是错的。3D 转盘每个角度都有各自正确的光照。
2. **两端不再各画一遍。** 现在 `ITEM` 表在 JS 和 C# 里各有一份实现，改一次要改两处，
   **必然漂移**。换成贴图之后这个风险直接消失，两端加载同一份 PNG。
3. **改型快。** 换一件物品（玫瑰换向日葵）只要改模型重渲；AI 生图得重新抽卡加抠像。

### 1.2 但收益被观众端的尺寸吃掉大半

物品在 960 宽画布上的实际直径，以及观众在直播间里实际看到的（按窗口 360 宽折算）：

| 档 | 物品 | 画布上 | **观众端** |
|---|---|---|---|
| 1 | 发卡 / 瓜子 | 44px | **16px** |
| 2 | 抱枕 / 手柄 | 112px | 42px |
| 3 | 花束 / 奶茶 | 152px | 57px |
| 4 | 戒指盒 / 相框 | 230px | **86px** |

**档 1 在观众端只有 16 像素**，还在以每秒四圈的速度翻滚、全程只飞 0.6 秒。
这个尺寸下 3D 建模的细节一个像素都落不到地。

**判断：档 1~2 做 3D 是纯浪费，档 3~4 有收益但不大，真正值钱的是上面第 2 条（两端统一）。**

### 1.3 粒子：不建议做 3D，收益是负的

| 理由 | 说明 |
|---|---|
| **没有深度可用** | 3D 粒子最大的卖点是景深和体积，而这个游戏是**纯平面构图**，底图是一张画、角色是预渲染帧，画面里根本没有 Z 轴 |
| **风格必然打架** | 底图 2D 手绘、角色 2D 预渲染帧，**只有粒子是 3D**，会非常突兀 |
| **性能数据全部作废** | 现有压测（帧均 1.63ms、p95 2.20）是在无 GPU 的 SwiftShader 上跑的，改 3D 后一条都不能用 |
| **两端分叉** | Unity 用原生粒子系统、网页用 WebGL，**同一份参数在两套系统里不可能对齐** |

**低成本的替代**：粒子保持 2D，但把纯色几何换成 **3D 渲出来的小贴图**（花瓣、照片、珍珠），
风格统一、性能不变。这条随时可做，且与下面选哪条路线无关。

## 二、三条路线

### 路线 A：3D 建模 → 离线渲成 2D 序列帧 → 两端当图片播 ★ 推荐

```
Blender 建模 → Toon 着色 + Freestyle 描边 → 渲 36 角度转盘（带 alpha）
   → 打包图集 → 网页 drawImage / Unity 同一份 PNG
```

- 拿到 3D 的**生产**优势（角度一致、批量、改型快、两端统一）
- 不付 3D 的**运行时**代价（引擎不动、性能不变、风格不裂）
- **管线已经跑通过**：桌面容器有 `blender 4.0.2`，2026-09-05 在三国项目上验证过，
  384px / 256 采样 / 826 面实测 **1.5 秒一帧**
- Blender 直接输出带 alpha 的 PNG，**不需要品红抠像**，省掉整条抠图管线和它的紫边坑

**工作量**（8 件全做）

| 步骤 | 估算 | 说明 |
|---|---|---|
| 程序化建模 | 半天 | 八件形状都简单：花束＝球阵列+锥，奶茶＝截锥+圆柱，戒指盒＝方盒+环面+八面体，相框＝方框。可用 Blender Python 脚本建，不需要手工雕 |
| Toon 着色调校 | **半天~一天，风险最高** | 见下方风险 |
| 渲染 | 约 10~20 分钟 | 8 件 × 36 角度 = 288 帧 × 约 2s |
| 引擎改造 | 半天 | `ITEM`/`SILH` 两张表从函数改成贴图采样，`draw` 里按 `rot` 选帧 |
| Unity 同步 | 半天 | `AmmoView.cs` 同样改法，**改完两端共用同一批 PNG** |

**体积**：288 张 384px 带 alpha ≈ 20MB。现有帧素材已 49MB，**再加 40% 需要打图集**，
否则首屏加载时间会明显变长。

**风险（这条路唯一真正的风险）**：

> **Toon 渲染很容易渲出"塑料感"，而那正是明令禁止的 C4D 立体质感。**

赛璐璐的硬边光影靠的是 Toon BSDF 的色阶数 + Freestyle 线宽，这两个参数没调好就会滑向
三维塑料。**这是整条路线成败的唯一关键，也是必须先做试点的原因。**

### 路线 B：引擎里跑真 3D 实时渲染

网页引入 three.js/WebGL 与 Canvas 2D 分层合成，Unity 换回原生 3D 管线。

**不推荐，五条理由**：

1. 网页零 WebGL，要新引一套渲染器并解决与 Canvas 2D 的合成、层序、坐标对齐
2. **Unity 版是网页画笔的 C# 翻译，走 3D 就脱离这套体系——"单一真源"架构破裂**，
   从此网页验证的东西和 Unity 跑的东西不再是一回事
3. 底图和角色都是 2D，只有物品粒子 3D，风格打架
4. 无 GPU 的验证环境失效，现有全部性能数据作废
5. **最要命的一条**：如果最终要的仍是 2D 观感（这是定死的美术方向），
   那实时渲出来的画面和离线渲的序列帧**看起来是一样的** ——
   你付了引擎改造、性能、架构分叉三份代价，换来一个肉眼无法区分的结果。

> 第 5 条是我反对路线 B 的核心。实时 3D 的价值在于"任意角度、动态光照、与场景交互"，
> 而这个玩法是固定机位、固定光照、平面构图，这三样一样都用不上。

### 路线 C：AI 生图画 2D 物品（原计划）

已有品红抠像管线，质感最好（厚涂/赛璐璐一步到位）。

**缺点**：只有一个角度，旋转仍靠整图 rotate，光影跟着转的穿帮问题**一点没解决**；
换型要重新抽卡；两端仍是两套贴图路径（虽然也能共用 PNG）。

## 六、试点结论：玫瑰花束（已完成）

**结果：路线 A 成立，四条判据全过。**

产物：`tools/3d/rose.py`（程序化建模+渲染，一个脚本跑完）、
`web/assets/items/rose_atlas.png`（36 帧转盘图集，6×6，单格 268px，2.3MB）。

### 6.1 四条判据

| 判据 | 结果 |
|---|---|
| 和 2D 角色在不在一个画风里 | ✅ 都是线稿描边＋平涂色块 |
| 有没有塑料光泽、立体投影 | ✅ 没有。Toon BSDF `smooth=0` 是硬边二分，不产生渐变高光 |
| 36 角度连播是否顺滑 | ✅ 真实尺寸胶片验证过，正面→顶视→背面→斜底连续 |
| 缩到观众端 69px 还认不认得出 | ✅ 一团红花配米色扎口，认得出 |

### 6.2 性能：帧均没有变化

压测条件比上一轮更严（每 110ms 一件礼物，上轮 300ms）：

| | 基线（矢量） | 3D 转盘贴图 |
|---|---|---|
| 帧均 | 1.63ms | **1.63ms** |
| 掉帧(>16.7ms) | 0.1% | 0.1% |
| 粒子 峰 | 575 | 874（池上限 1200） |

`drawImage` 一张贴图比现场画几十个 path 还便宜一点，正好抵掉图集采样的开销。

### 6.3 耗时实测（72 核，Cycles CPU）

- 36 帧 / 320px / 160 采样 / 双 lineset 描边：**2 分 06 秒**（约 3.5s/帧）
- 建模＋调参迭代 7 轮，每轮渲 6~8 帧验证，单轮约 30 秒
- **渲染从来不是瓶颈，调形和调风格才是**

### 6.4 踩到的六个坑

1. **`linesets.new()` 建出来的 lineset 不自带 linestyle**，直接设 `.color` 会
   `AttributeError: 'NoneType'`。要显式 `bpy.data.linestyles.new()`。
2. **`join` 之后物体原点留在最后一个 active 物体上**，直接转 `rotation_euler`
   是绕原点转，花头甩着画大圈飞出画外。必须 `origin_set(type='ORIGIN_GEOMETRY')`。
3. **描边必须分两档**。只用一档：粗了内部花瓣叠成一团黑，细了外轮廓撑不住。
   建两个 lineset —— 外轮廓 `silhouette` 2.6，内部 `border` 1.1。
4. **花瓣排布半径必须远小于花瓣宽度**，否则彼此够不着，渲出来是一堆散开的红碎片。
   顶边还要压成弧、宽度走 sin 曲线，直顶边加卷曲就是一根尖刺，整团读成蓟花。
5. **圆锥从正底看的投影是它最宽处那个圆**，把底部收尖是白费功夫。底视要好看，
   得让花团显著宽于扎口（真实捧花约 2~3 倍，我第一版只有 1.7 倍）。
6. **转轴不能选垂直轴**。七朵花是环形排列的、近似轴对称，绕垂直轴转几乎看不出
   变化；要绕水平横轴翻滚，才能依次看到正面、顶部、背面、底部——体积感全在这里。
   同时转轴要给一个固定倾角（0.75 rad），纯绕横轴会转到正底面，那一帧只剩一个灰梯形。

### 6.5 引擎侧改动（`ammo.js`）

新增 `SPRITE` 表 + `loadSprites()` + `cellOf()`，`GIFT` 加一个 `spin` 字段。
**矢量画法全部保留**：加载失败、或带 `?nosprite=1`，自动退回 `ITEM` 函数——
`?sim` 那条分支不加载任何素材，必须能退。

两处非显然的地方：

- **贴图本体不转 canvas**。转盘每一格自己就是那个角度渲好的，再叠 2D 旋转会变成
  "又翻又转"，而且光影跟着 canvas 一起转——那正是换 3D 要解决的问题。
- **残影分两套参数**。矢量的 `SILH` 是刻意简化过的轮廓（花束就是七个圆），
  四个叠起来仍读作影子；贴图剪影带着全部细节，同样画四个就糊成一大团暗红，
  比本体还抢眼。贴图改成两个、浓度减半。

### 6.6 转速要重新定

矢量物品转的是一张平面图，快了只是晃眼；**贴图必须在飞行途中转够一圈以上**，
观众才看得出它有厚度。重投飞完全程约 0.65 秒，`spin: 14`（rad/s）约合一圈半。

### 6.7 铺开到其余三件之前要先解决的

**体积**：一件 2.3MB，四件 9MB，八件 18MB。现有帧素材已 49MB。
铺开前应先试 webp 或把单格降到 200px，预计能压到三分之一。

## 七、铺开阶段（2026-09-20）

用户要求："所有弹幕礼物以及命中特效，除了玫瑰花束，都优化成类似玫瑰花束那种
看起来有体积感的"。于是从"试点一件"进到"铺开八件 + 命中粒子"。

### 7.1 体积卡点解决了，根因不是尺寸也不是帧数

第六节记的卡点是"一件 2.3MB，八件 18MB，铺开前先试 webp 或把单格降到 200px"。
实测下来**降尺寸和砍帧数都是拿画质换体积，不必要**：

| 同样 36 帧 268px | 体积 |
|---|---|
| PNG（原） | 2433 KB |
| WebP 无损 | 1625 KB |
| **WebP q=88** | **408 KB** |

根因是 **PNG 的无损编码**对付不了 Toon 平涂 + 硬描边这种图。换 WebP 之后：
**alpha 通道逐像素无损**（WebP 的 alpha 始终单独无损压，实测差值恒为 0），
RGB 平均差 4.3/255，2 倍放大肉眼分不出。q 再往上给收益极小（q=100 也只降到
3.39，因为剩下的差异来自 lossy WebP 的 YUV420 色度下采样，不是量化）。

八件物品按各自档位的单格边长（档1 96 / 档2 160 / 档3 272 / 档4 336）估算
总计 2.5~3 MB —— 八件加起来还不到原来一件的一倍半。

### 7.2 管线拆成了框架 + 建模脚本

- `tools/3d/common.py`：Toon 材质、硬光 + 暖灰环境、正交相机、Freestyle 双档描边、
  `join_all` 原点归心、`render_turntable` 绕横轴翻滚。**八件共用，改一处等于改全套风格。**
- `tools/3d/pack_atlas.py`：并集裁切 → 下采样 → 打包 WebP → **自动算出 `scale`**。
- 物品脚本只写建模，十几行到几十行。

两条尺寸约定：**主体直径做成 2.0 个 Blender 单位，相机 ortho 固定 3.3**。
`scale = 并集边长 / (渲染边长 × 2.0/3.3)` —— 并集比物体大多少就放大多少倍回去。
等价性验证：用新框架重写的 `bouquet.py` 跑出来 `scale=1.34`，与当初手填进
`ammo.js` 的值完全一致。

### 7.3 描边宽度必须跟着格子大小走

`common.py` 的 2.6 / 1.1 是给 272px 的物品格子定的。粒子格子只有 80px，
**同样的绝对宽度占比就是三倍**，整颗粒子会被描边吃掉，远看只剩一团深色。
实测 2.6 / 1.7 / 1.2 三档（真实绘制尺寸下对比），粒子取 **1.7**：
1.2 在明亮客厅底图上撑不住可见度，2.6 把星星吃成一坨。

赛璐璐里小东西的线**相对**粗一点是对的，粗三倍不是。

### 7.4 命中粒子：白贴图 + 运行时染色

粒子颜色是配方在 spawn 时**逐颗**定的（`i % 5 ? A : B` 这种），烧死在贴图里
配方就没法调色了。所以贴图一律渲白，引擎用 `multiply` 乘上目标色 ——
亮面变目标色本身、暗面变它的暗调，**二分光影原样保留**。
（`multiply` 会把透明区的 alpha 也抬成 1，要再 `destination-in` 把轮廓切回来。）

**描边不能渲成角色线稿那个暖黑。** 它也会被一起乘：白羽毛乘白 = 描边还是深棕，
在近白的羽毛上重得像瓜子壳，而配方原本给的描边是浅灰紫。改渲 **55% 中性灰**
之后，描边自动等于"主色 × 0.55"，也就是这颗粒子自己的暗调 ——
浅羽毛得浅灰边、深玫红花瓣得暗红边，配方对描边色的控制以另一种形式还回来了。

### 7.5 符号类粒子的转轴要换

星星和爱心是**符号**，观众读的是"星星"这个概念而不是一个立体物件。
绕横轴翻面时 12 帧里有 4 帧只剩一团皱纸，符号性全没了。
改成绕**观察轴**（`axis='Y'`）转：正面始终朝观众，靠 `common` 的固定倾角
仍然看得出厚度。花瓣、羽毛、碎片、照片卡照旧绕横轴翻面 —— 它们在空中翻面
本来就是对的。

### 7.6 贴图转盘的角速度两头受夹

矢量物品转的是一张平面图，转多快都只是晃眼。贴图转的是真转盘：

- **下限**：必须在飞行途中转够一圈以上，观众才看得出它有厚度。
  重投全程约 0.65 秒，一圈需要 9.7 rad/s —— 矢量时代 heavy 的默认值 4.5 连半圈都不到。
- **上限**：每帧换的格子不能太多。60fps、36 格、每格 10°，
  volley 的默认值 26 rad/s 就是每帧跳 2.5 格，那不叫旋转，那叫乱闪。

两头一夹，八件都落在 **14~15** 这个窄带里，跟体量没什么关系了 ——
所以八件现在全部显式写 `spin`，不再按 style 取默认值。

另：`fire()` 里"处决弹转速减半"那句原先写在 `p.vrot` 赋值**之前**，
改的是对象池里上一发留下的旧值，从来没生效过。已挪到赋值之后。

### 7.7 画面内旋转与转盘旋转要分开给

贴图已经在转了，再让 canvas 全速跟着转就是"又翻又转"，而且会把渲好的光影
一起转走 —— 那正是换 3D 要解决的问题。但完全不转 canvas 又僵。
最后是**分两份**：转盘格子走 `p.rot` 全速（物体在翻面），
canvas 只跟着转四分之一（它在画面里打旋）。

### 7.8 细长件的绘制倍率要手工调

`pack_atlas` 算出的 `scale` 对物品是准的（主体直径占满 2.0），
但粒子里有细长件 —— 羽毛长宽 1:2.2，在正方形格子里只占一半宽度，
照算出来的倍率画就比矢量版细一圈，在画面上碎成一片瓜子壳。
`feather` 1.03→1.40、`debris` 0.83→1.00 是实测调的，表里标了原值。

绘制尺寸还必须取**正方形**：格子是按所有角度的并集正方形裁的，物体在里面
保持自己的长宽比，再按 `w×h` 去拉伸等于把比例乘两遍，羽毛会被拉成一根面条。
