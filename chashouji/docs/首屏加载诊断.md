# 首屏加载诊断（2026-10-01，引擎负责人；只诊断，没改代码）

用户反馈："网页打开很卡，半天刷不出内容。"正式页 http://1.14.252.30:40235/index.html（桌面 /home/op/chashouji/web）。

## 0. 结论

- **打开后先看到标题和按钮（约 3 秒），画面区一直是黑的。**20 Mbps 下要 25.6 秒才出第一帧，5 Mbps 下要 66.1 秒。按钮的事件也要等到这一刻才绑上，所以此前点了没反应。
- **根因 1（主因）：`main.js boot()` 把 330 个请求全部 await 完才画第一帧。**首帧前实收 38.8 MB，其中首帧真正用到的只有约 6.4 MB。60 人三人组、礼物图集、档 4 素材、结算图、档 4 出场视频全都排在首帧前面。
- **根因 2：boot 是 5 段串行 await。**每段都要等上一段收完才开始；其中主角姿势图 81 张 4.6 MB 一张不落地全等。
- **根因 3：服务器是 `python3 serve.py`（SimpleHTTPRequestHandler），有四个问题：**
  - HTTP/1.0 不保持连接，每个文件都新建连接、从 TCP 慢启动开始；
  - 不压缩；
  - `Cache-Control: no-store`，每次打开都重下 38.8 MB，回访也一样；
  - 不支持 Range，4 个档 4 视频在首屏阶段占着连接和带宽。
- **只把首帧不需要的东西挪出首屏，就能实测把首帧从 25.6 秒降到 9.7 秒（20 Mbps）、从 66.1 秒降到 16.3 秒（5 Mbps）。**再加上姿势图分批和服务器修复，估计首帧能到 20 Mbps 约 2~3.5 秒、5 Mbps 约 3~5 秒。
- 图片格式不是原因：全部是 webp，最大单图 621 KB。服务器用的是多线程（ThreadingHTTPServer），也不是单线程的问题。

## 1. 测法

- 在桌面容器里起一个新的 headless Chrome（/usr/bin/google-chrome）。每次都是新的 context，并用 `Network.setCacheDisabled` 关掉缓存。
- 走**公网地址** 1.14.252.30:40235，不走本机回环。
- 用 CDP 的 `Network.emulateNetworkConditions` 限速：下行分别为 20 Mbps 和 5 Mbps，RTT 加 50 ms，上行 2 Mbps。另外跑了一次不限速作对照。
- 脚本在 `tools/load/`：
  - `measure.py <Mbps> <RTT> <输出>` 记录瀑布数据和页面里程碑；环境变量 `BLOCK=<正则>` 可以把匹配的请求在页面层 abort 掉，用来实测"首屏不加载这些"时的首帧时间；
  - `cat.py` 按类别汇总；
  - `prof.py` 做 CPU profile。
- 页面里程碑是注入的 init script 记录的，时间都从导航开始算：
  - **首帧** = 主循环第一次调用 `requestAnimationFrame(frame)`。boot 跑完才会调它，启动期间页面上没有别的 rAF。
  - **画面非空** = `#bg` 画布中心像素第一次不透明。
  - **可操作** = `#hitL.onclick` 第一次被绑上。礼物按钮的 onclick 和它在同一段代码里绑定，都在 boot 的所有 await 之后。
  - FCP 取自 `performance` 的 paint 条目。
- **字节数用的是 `Network.dataReceived` 的实收量。**被中途 abort 的视频请求，`loadingFinished` 不给大小，所以不能用 `encodedDataLength`。第一轮就是这样漏算了 7 MB。
- 原始数据：
  - 瀑布 CSV：`shots/load/瀑布_{0,20,5,20b,5b}.csv`，每个请求的开始 / TTFB / 结束 / 实收 / 状态 / 是否在首帧前完成 / 协议 / 压缩 / 缓存头；
  - 里程碑：`shots/load/里程碑_*.json`；
  - `b` 后缀 = 首帧不需要的请求被 abort 掉的那一轮。

## 5. 根因（每条都有数据）

### R1 首帧前把全部素材都 await 完（主因）
- 首帧前实收 38.8 MB，首帧用到的只有 A + B + C 光效 + 当前姿势，约 6.4 MB。
- **实测**：在页面层把 D 类全部 abort 掉，代码不改（各 loader 失败时本来就不阻塞，resolve 成 false / null），首帧从 25.6 s 降到 9.7 s（20M，−62%），从 66.1 s 降到 16.3 s（5M，−75%）。页面照常跑，没有 error。
- 这些 D 类素材要等有人送了对应礼物才用得上。首帧之后在后台排队下载就够（见第 6 节的队列和兜底）。

### R2 串行 await 和 81 张姿势图全等
- ① ~ ⑤ 五段首尾相接，每段都要多付一次 RTT，段与段之间带宽也用不满。
- 第 ③ 段是 abort D 类之后剩下的最大一块：20M 下 4.4~9.4 s（5.0 s），5M 下 7.3~15.9 s（8.6 s），占"首屏只加载必需"之后首帧时间的一半以上。
- `PoseView.draw` 遇到没加载的图只是 `return`（main.js 1880 行），所以不能直接不等，要先准备一个兜底姿势。

### R3 档 4 出场视频在首屏时段抢连接
- `intro.js init()` 给 4 个 webm（合计 15.0 MB）设了 `preload='auto'`。服务器不支持 Range，每个请求都返回 200 + 整个文件；浏览器媒体栈读够自己要的就 abort，然后重新请求。
- 5M 下这 4 个请求从 3.8 s 占到 25.4 s，实收 6.39 MB。
- 同一时间段的第 ① 段（背景 0.76 MB）因此用了 5.7 s；视频被 abort 掉的那一轮只要 1.8 s。

### R4 服务器（`web/serve.py`）
实测响应头：`HTTP/1.0 200 OK`、`Server: SimpleHTTP/0.6 Python/3.12.3`、`Cache-Control: no-store, must-revalidate`，没有 Content-Encoding，没有 Accept-Ranges。

| 问题 | 数据 | 影响 |
|---|---|---|
| HTTP/1.0，不保持连接 | 本机工作区经公网拉同样 40 个 trio 图（7.6 MB）：<br>· 现服务，1 条连接：4.1 Mbps；6 条连接：**19.4 Mbps**；<br>· 同目录临时起一个 HTTP/1.1 的服务（只改 `protocol_version`），1 条连接：9.8 Mbps；6 条连接：**45.0 Mbps**；<br>· 现服务 16 条连接：47 Mbps（说明链路本身够宽）。<br>临时服务测完已关 | 浏览器对同一个 host 只开 6 条连接。每个文件都从慢启动开始，所以对用户来说有效带宽上限大约是 20 Mbps，带宽再大也用不上 |
| 不压缩 | 13 个 js 763 KB → gzip 282 KB；world.json 371 KB → 35 KB | 首屏关键路径上多 0.82 MB（5M 下约 1.3 s） |
| `no-store` | 每次打开 38.8 MB 全部重下 | **回访一样慢。**加 no-store 原本是为了"改了 js 部署上去浏览器还看到旧的"（serve.py 文件头）。换成 `no-cache` 同样保证拿到新版本：`SimpleHTTPRequestHandler` 本来就会处理 If-Modified-Since，文件没变时回 304 |
| 不支持 Range | 视频每次都是 200 + 整个文件 | 视频不能边下边播，也不能 seek，见 R3 |
| listen backlog 5 | `ss -ltn` 看到 40235 的 Send-Q 是 5（socketserver 默认的 request_queue_size） | HTTP/1.0 每个文件都新开连接，多人同时打开时容易排满。**没有做多人并发实测** |
| 多线程 | ThreadingHTTPServer，本机回环单文件 413 MB/s | 不是瓶颈 |

### 不是原因
- **图片格式和尺寸**：
  - 359 个 webp、105 个 png。首屏加载的全部是 webp，最大 621 KB。
  - 三人组图集 8 格一张，1736×1676 左右，约 600 KB。
  - 物品图集 6×6，单格 130~336 px；粒子图集单格 80 px。
  - 单格尺寸和画布 960 宽的显示尺寸在同一个量级。压缩率和分辨率还有余地，但省下的远小于"不在首屏加载"，是次要项。
- **JS 执行**：约 2.4 s，是测量环境的副作用，见第 2 节。

## 6. 修复方案和预估收益

| # | 方案 | 省多少（实测 / 估算） | 要改什么 |
|---|---|---|---|
| **P1** | **首屏只 await 必需的 A + B + C 光效**。第 ④ 段的结算图和第 ⑤ 段整段，从 await 改成首帧之后放进一个后台预取队列（见下）；boot 拿到必需的素材就起主循环、绑按钮 | **实测**：首帧 20M 25.6 → 9.7 s，5M 66.1 → 16.3 s。首帧前的数据量从 38.8 MB 降到 7.4 MB。这个数已经包含 P3 的效果（那一轮视频也被 abort 了） | main.js boot；各 loader 本来就支持失败不阻塞 |
| **P2** | **姿势图分批**：只 await 待机那 5 张（n0、nL1、nL2、nR1、nR2，约 0.3 MB），其余 76 张排进预取队列的最前面。`PoseView.draw` 缺图时画同组已加载的基础姿势（例如 `aK_g1` 缺就画 `aK`，基础姿势缺就画 n0），不能画空 | 估算：关键路径少 4.3 MB。第 ③ 段在 20M 下 5.0 s → 约 0.5 s，5M 下 8.6 s → 约 1 s。**叠在 P1 上：20M 约 5 s，5M 约 8.5 s** | main.js boot、PoseView |

**全部做完后的首帧估算**：
- 关键路径 ≈ A（gzip 后 0.3 MB）+ 背景 0.43 MB + 光效 0.28 MB + 5 张姿势 0.28 MB + 头像 ≈ **1.3 MB**，另有 3~4 段串行往返。

- 20 Mbps：≈ **1.5~3.5 s**。
- 上下限的差别主要就在脚本执行那一项。

### 送礼时素材还没下完：兜底（原则：画面立刻有反应，不出现空白，不卡住）
- **任何礼物**：点下去的那一刻先把这件礼物要用的素材**插到队列最前面**。HUD 的拉力、名字条等数值反馈照常立刻生效；它们都是程序画的，不依赖素材。
- **档 1 / 2 飞行物品**：`Ammo` 和 `Particles` 本来就有矢量画法兜底（ammo.js `loadSprites`、fx.js `loadShapes` 的注释："加载不到就退回各自的矢量画法"）。第一发用矢量飞过去，图集到了之后自动换成转盘贴图。**不会空白。**
- **档 3 三人组**：
  - 每个槽位只从**已经加载好的人**里随机抽，名单抽人本来就是"做好的人才参与抽"的逻辑，加一条"已加载"即可；
  - 某个槽位一个都还没加载好时，就抽定这个人，把他的 3~4 个文件插到队首，并把 `summon(_, wait)` 的 wait 设成"加载完"（trio.js `summon` 本来就有 wait 参数，按 wait 延后进场）；
  - 5M 下一个人 0.1~0.7 MB，要 0.2~1.1 s。先加载好的槽位先进场，读起来像是"陆续赶到"。
- **档 4**：
  - 视频还没缓冲够（`readyState < 4`）就跳过视频，人直接进场。和 `?introvideo=0` 走的是同一条路径，现成可用；
  - 档 4 人物贴图没到时，同样按 wait 延后进场，一张 100~300 KB。
- **结算图**：`Result.load` 失败时退回纯色板（result.js 注释"缺素材时结算退到纯色板"），也不会空白。
- **姿势图**：见 P2，退回同组的基础姿势。

## 7. 没验证 / 风险
- 真机上的脚本执行时间（估 ≤ 0.5 s），这台桌面是 2.4 s。
- RTT 按 50 ms 模拟。本机工作区到这台服务器实测 TCP 建连约 72 ms，用户那边可能更大，更大的 RTT 会放大 R2 和 R4 的串行成本。
- headless Chrome 对 `preload='auto'` 的媒体读了约 6.4 MB 就 abort。桌面版 Chrome 可能读得更多，所以 R3 在用户那边只会更重。
- 多人同时打开（backlog 5）没有实测。
- P2、P4 的收益是按实测的段时间和吞吐比例推算的，没有实装验证；P1（含 P3）是实测。
